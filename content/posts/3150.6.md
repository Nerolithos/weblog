# CSC3150 Lecture14  Memory: vMem, segments and pages

## vMem & Virtual Address

- Uniprogramming：同一时间只有一个应用在运行，可访问任何实际内存，实际独占机器；

- **Primitive multiprogramming**：没有翻译/保护的 multiprogramming，尝试通过 loader/linker 防止地址 overlap。若没有 protection，bug 可以跨程序破坏，甚至影响 OS。

多线程共享硬件，就需要 (通过 Virtualization) 资源复用 multiplexing，比如已经讲完的 scheduling (CPU 复用)、和接下来的 vMem (内存复用)。

进程/kernel 不能用同一个物理内存位置，比如跨进程线程不能互相访存。进程不能因为使用相同地址就互相覆盖。**Protection** 进程不能随意读取其他进程/内核的私有内存—— kernel 隔离 (Dual mode)、进程间保护、不同页 (memory page) 有各自行为 (如 Read only、Invisible to User...)

现代解决办法是区分：

- Virtual Address (VA)：程序使用的地址 (CPU 看到的)。
- Physical Address (PA)：数据在实际 RAM 中的位置，VA 不必等于 PA (Memory 看到的)。
- MMU (Memory Management Unit)：硬件负责地址翻译 (**Translation**)，**Controlled Overlap：需要时可以让两个进程共享同一块物理内存** (不同 state 的线程不可发生 PA 碰撞；反过来需要通信时可以控制 overlap)

[Address space](https://blog.nero-lithos.com/posts/3150.1/#address-space-%E5%86%85%E5%AD%98%E5%9C%B0%E5%9D%80%E6%9C%89%E5%BA%8F%E4%B8%94%E5%BA%9E%E5%A4%A7%E7%9A%84%E5%B9%BB%E8%A7%89)：存在 translation 时，程序在 Virtual Adress space 运行；没有时就是 PA。

**为什么不能让 OS 处理每一次内存访问**？因为 CPU 每秒可能执行大量的 Load、Store、I-Fetch。如果每次都切换到 Kernel，开销会极其巨大。思路是：

- 正常访问：MMU 硬件直接处理地址翻译。

- 特殊情况：触发 Page Fault 等异常，由 OS 处理。

> ⚠️ Virtual Memory 不是指硬盘上的虚拟内存文件，而是一套虚拟地址空间和映射机制。 使用磁盘作为后备存储只是它支持的功能之一。

</br>

### Basic Addressing Calculation

在 k-位机器上，地址有 k bits，且按字节寻址 Byte Addressing：**Address Space Size = 2<sup>k</sup> Bytes**，比如 32、64 位机分别有 4 GiB ≈ 4 billion B、16EiB 的虚拟空间 (寻址空间)

反之，计算 4 KiB 的内存页需要多少个 Offset bits：4 x 1024 b = 4096 b = 2<sup>12</sup> 即 12 bits。

32-bit Address Space 可以存放 2<sup>32</sup>/4=2<sup>30</sup> 个 32-bit Integer。

(KiB, GiB 这类单位表示严格按二的幂定义：1GiB = 2<sup>10</sup> MiB = 2<sup>10</sup>x2<sup>10</sup> KiB = 2<sup>10</sup>x2<sup>10</sup>x2<sup>10</sup> B = ...x8bits；一般等同于 KB, GB，但后者常有十进制混用)

## Base&Bound Protection

[B&B](https://blog.nero-lithos.com/posts/3150.1/?hl=Base+and+Bound#memory-protectionbb-and-addressing) 是最简单的硬性内存保护，B&B Regs 由 Kernel 管理。

程序准备被运行经过：Compile time (E.g. gcc)、Link/Load time ("ld" for UNIX)、Execution time (E.g. dynamic libs (postponed linking))；地址可以在任意时间段内被限制到最终范围 (取决于 OS 和硬件支持)

### B&B without Translation

没有 Translation 的早期系统，如 Win3.x 以前 (Primitive Multiprogramming) 可以直接将程序装入物理内存。

假设程序 A 占用 `0x0000–0x1FFF`，程序 B 占用 `0x2000–0x3FFF`，这会出现两个问题：

- 程序 B 的地址需要根据实际加载位置调整 (**Relocation**)。
- 如果程序 A 错误访问 `0x2500`，可能破坏 B 的数据。

因此，操作系统需要**对每个进程允许访问的地址范围**进行检查。

无翻译的 Base 和 Bound 就是 PA 范围边界—— Valid: **Base ≤ address < Bound**。

需要 **[Relocating](https://blog.nero-lithos.com/posts/3060.8/?hl=relocation#relocation-1) Loader**：程序在加载时事先确定地址属于物理 B&B 约束范围。⚠️ No addition on address path: 不会在每次内存访问时加 Base (offset)。无翻译的缺点：任何程序都可以被 link/load 到同个 Physical Address space 区域。

</br>

### B&B with Translation

翻译使保护更容易，⚠️ **程序使用从零开始的虚拟地址，硬件自动加上 Base**：PA = Base + VA —— Valid: **0 ≤ address < Limit** (Limit 是虚拟偏移量)

虚拟地址不等同于硬件地址，由 MMU (HW relocation) 决定最后访问哪一个 physical address。运行时 (**on-the-fly**) 动态通过加偏移量计算物理地址。

</br>

### B&B Insufficiency

- Fragmentation (内存碎片化)：连续分配给进程相同大小的空间容易产生无法利用的空隙 (Internal and External of blocks)
- Missing support for Sparse Address Space：Code、Heap、Stack 之间可能有大量未使用地址，不应该全部占据物理内存。
- IPC (Sharing) 困难：不同进程难以灵活共享部分内存。

于是引出 Segmentation

## Segmentation 分段

分段的思想是：不再把一个进程当成一整块连续内存，而是分成多个独立的 Segment (储存单元细化)，各自有 base&limit (B&B w translation)

例如 Code、Data、Stack 可以分别放在物理内存的不同位置，甚至中间隔着别的进程所属地址。

</br>

### 实现分段

一个 VA 拆成两部分：Segment ID (`Seg #`)、Offset (每个段各自从 0 表示偏移)

处理器维护一个 **Segment Table** (较小，**存在 CPU Processor 而非内存**)，以保存每个分段的 **Base-Limit pair、Validity** (用 1bit 表示是否允许用该段-V/N)。物理内存块数 = `#entries of table`

翻译步骤：

1. 根据 Segment ID 找到对应 (映射) 表项；
2. 检查 Valid Bit；
3. 检查 `Offset < Limit` (防止 out-of-range Error)；
4. **计算 `PA = Base + Offset`**。

</br>

### Example: 16b-VA Segment Translation

16-bit VA 前 2b 表示 Segment ID，剩余 14b 表示 Offset。

![](https://img.nero-lithos.com/posts/%E6%88%AA%E5%B1%8F2026-11-09%2015.47.45.png)

例：VA = `0x4050`：4<sub>HEX</sub> = 0100<sub>BIN</sub>，属于 01 (data) segment；Base = `0x4800`，Limit = `0x1400`；因为 `0x0050 < 0x1400`，访问合法；PA = `0x4800 + 0x0050 = 0x4850`

实际汇编案例中，Instruction Fetch 和 Data Load 都需要地址翻译。例如：

- PC = `0x0364`，取指令的物理地址是 `0x4364`。
- 指令读取的虚拟数据地址是 `0x4050`，对应物理地址 `0x4850`。

这两个地址要分别翻译，不能因为已经翻译了 PC，就直接把数据地址当成物理地址。

</br>

### Pros and cons of Segmentation

- 每次 Load、Store、I-Fetch 都要翻译

- Segmentation 支持不同大小的连续内存块，对 Sparse Address Space 高效，但也因此存在 External Fragmentation (外部碎片：free gaps of spaces between chunks)。这些内存中的空洞，可以允许 Stack/Heap 向 Valid range 之外增长，但也是浪费空间
- Internal Fragmentation：Segment 中不是所有信息都是必要 (存在内存中) 的 —— 需要 **finer granularity** controls

- Segment Table 需要保护：比如 code read-only；data, stack r&w，后文的 Paging 规则一致

- Segment Table 较小，从而存储在 CPU 而非内存；

  **Swapping**：当内存不足时发生 **Context Switch**，为了给下一个进程腾空间，可能把部分或全部 Process Segment Memory 移到 disc，但移动大块数据的开销很高

## Paging 分页

分页是分段产生的 fragmentation 问题的解决方案

> Paging 和 Segmentation 的根本区别：分段使用大小可变的块，分页则把内存划分为固定大小的块。Page 通常比 Segment 小 (1~16KiB)，否则又会有 Internal fragmentation，从而一个段需要占用多页表示。

- Virtual Memory 中的块叫 Page；

- Physical Memory 中的块通常叫 Frame (Page Frame)，每块互相等价 (equivalent)；

- **每个进程维护一个 Page Table** (存储在 Memory) 记录每个 Virtual Page 映射到哪个 Physical Frame，

  以及每页各自的的 Validity, Read, Write 权限；

- 可以用一个 bitvector 表示各个 Physical Page 是 (0) 否 (1) 空闲

固定大小意味着任何空闲 Frame 都能容纳一个 Page，不需要寻找特定大小的连续空间。

> ⚠️ Paging 最重要规律：**Offset 不变** (虚拟-物理页大小必然相等)。Page Table 只负责将 VPN (Virtual Page Number 即 VP\#) 转换成 PFN (Physical Frame Number 即 PP\#) —— \[VPN | Offset] —page table→ \[PFN | Offset]

假设 **Page Size = 2<sup>p</sup> B，意味着 Offset 需要 p bits** 来表示每页中的所有位置，剩余位数为 VPN (2<sup>VPN</sup> bits ≤ Page table 的 entry 数)：

⚠️ **VA = VPN x Page_size + Offset = 2<sup>p </sup>VPN + p**，VPN 就是分页的商 (⌊VA/2<sup>p</sup>⌋)，Offset 是余 (VA mod 2<sup>p</sup>)

- **PA = PFN x Page_size + Offset**

- 当 VPN > Page table size，Access Error (out-of-bound)

如果访问一个无效或权限不允许的 Page，可能产生异常。Page Fault 不一定代表程序崩溃：例如合法的按需分配或换入页面可以由 OS 处理；非法访问则可能导致程序终止。

Stack 向低地址增长时 (需要更多空间)，OS 可以为新的虚拟页分配物理 Frame，并更新 Page Table。**不需要在原 Stack 所在物理地址旁边**找到连续空间。 这正是 Paging 相对于 Segmentation 的重要优势。

</br>

### Example: 4B Pages

Page Size = 4 bytes，所以 Offset 只需要 2 bits；Page Table:

| VPN  | PFN  |
| ---- | ---- |
| 0    | 4    |
| 1    | 3    |
| 2    | 1    |

我们翻译 Virtual Address `0x06`：

1. `0x06 = 6`，所以 VPN = `6 // 4 = 1`；
2. Offset = `6 % 4 = 2`；
3. Page Table 查得 VPN 1 → PFN 3；
4. PA = `3 × 4 + 2 = 14 = 0x0E`。

</br>

### Page Sharing

不同进程拥有各自的 Page Table，但它们的不同 VPN 可以指向同一个 PFN，典型用途包括共享库 (User-level system lib (execute-only))、共享 (Binary) 代码页以及进程间共享内存。

---

| 机制                   | 地址翻译方式               | 优点                 | 主要问题                         |
| ---------------------- | -------------------------- | -------------------- | -------------------------------- |
| Base & Bound（无翻译） | 检查物理地址范围           | 简单                 | 需要 relocation、灵活性差        |
| Base & Bound（有翻译） | Base + VA                  | 隔离进程             | 连续分配、I&E Fragmentation      |
| Segmentation           | Segment Base + Offset      | 逻辑分段、可共享     | 段落连续、E-Fragmentation        |
| Paging                 | PFN x Pagesize + 原 Offset | 非连续分配、易于共享 | Page Table 开销、I-Fragmentation |

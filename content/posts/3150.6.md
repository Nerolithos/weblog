# CSC3150 Lecture14  Memory: vMem, Segments and Pages

## vMem & Virtual Address

- Uniprogramming：同一时间只有一个应用在运行，可访问任何实际内存，实际独占机器；

- **Primitive multiprogramming**：没有翻译/保护的 multiprogramming，尝试通过 loader/linker 防止地址 overlap。若没有 protection，bug 可以跨程序破坏，甚至影响 OS。

多线程共享硬件，就需要 (通过 Virtualization) 资源复用 multiplexing，比如已经讲完的 scheduling (CPU 复用)、和接下来的 vMem (内存复用)。

进程/kernel 不能用同一个物理内存位置，比如跨进程线程不能互相访存。进程不能因为使用相同地址就互相覆盖。**Protection** 进程不能随意读取其他进程/内核的私有内存—— kernel 隔离 (Dual mode)、进程间保护、不同页 (memory page) 有各自行为 (如 Read only、Invisible to User...)

现代解决办法是区分：

- Virtual Address (VA)：程序使用的地址 (CPU 看到的)。
- Physical Address (PA)：数据在实际 RAM 中的位置，VA 不必等于 PA (Memory 看到的)。
- CPU MMU (Memory Management Unit)：硬件负责地址翻译 (**Translation**)，**Controlled Overlap：需要时可以让两个进程共享同一块物理内存** (不同 state 的线程不可发生 PA 碰撞；反过来需要通信时可以控制 overlap)

[Address space](https://blog.nero-lithos.com/posts/3150.1/#address-space-%E5%86%85%E5%AD%98%E5%9C%B0%E5%9D%80%E6%9C%89%E5%BA%8F%E4%B8%94%E5%BA%9E%E5%A4%A7%E7%9A%84%E5%B9%BB%E8%A7%89)：存在 translation 时，程序在 Virtual Adress space 运行；没有时就是 PA。

**为什么不能让 OS 处理每一次内存访问**？因为 CPU 每秒可能执行大量的 Load、Store、I-Fetch。如果每次都切换到 Kernel，开销会极其巨大。思路是：

- 正常访问：MMU 硬件直接处理地址翻译。

- 特殊情况：触发 Page Fault 等异常，由 OS 处理。

> ⚠️ Virtual Memory 不是指硬盘上的虚拟内存文件，而是一套虚拟地址空间和映射机制。 使用磁盘作为后备存储只是它支持的功能之一。

</br>

### Basic Addressing Calculation

在 k-位机器上，地址有 k bits，且按字节寻址 Byte Addressing：**Address Space Size = 2<sup>k</sup> Bytes**，比如 32、64 位机分别有 4 GiB ≈ 4 billion B、16EiB 的虚拟空间 (寻址空间)

反之，计算 4 KiB 的内存页需要多少个 Offset bits：4 x 1024 b = 4096 b = 2<sup>12</sup> 即 12 bits。

32-bit Address Space 可以存放 2<sup>32</sup>/4=2<sup>30</sup> 个 32-bit Integer。

(KiB, GiB 这类单位表示严格按二的幂定义：1GiB = 2<sup>10</sup> MiB = 2<sup>10</sup>x2<sup>10</sup> KiB = 2<sup>10</sup>x2<sup>10</sup>x2<sup>10</sup> B = ...x8bits；一般等同于 KB, GB，但后者常有十进制混用)

## Base&Bound Protection

[B&B](https://blog.nero-lithos.com/posts/3150.1/?hl=Base+and+Bound#memory-protectionbb-and-addressing) 是最简单的硬性内存保护，B&B Regs 由 Kernel 管理。

程序准备被运行经过：Compile time (E.g. gcc)、Link/Load time ("ld" for UNIX)、Execution time (E.g. dynamic libs (postponed linking))；地址可以在任意时间段内被限制到最终范围 (取决于 OS 和硬件支持)

### B&B without Translation

没有 Translation 的早期系统，如 Win3.x 以前 (Primitive Multiprogramming) 可以直接将程序装入物理内存。

假设程序 A 占用 `0x0000–0x1FFF`，程序 B 占用 `0x2000–0x3FFF`，这会出现两个问题：

- 程序 B 的地址需要根据实际加载位置调整 (**Relocation**)。
- 如果程序 A 错误访问 `0x2500`，可能破坏 B 的数据。

因此，操作系统需要**对每个进程允许访问的地址范围**进行检查。

无翻译的 Base 和 Bound 就是 PA 范围边界—— Valid: **Base ≤ address < Bound**。

需要 **[Relocating](https://blog.nero-lithos.com/posts/3060.8/?hl=relocation#relocation-1) Loader**：程序在加载时事先确定地址属于物理 B&B 约束范围。⚠️ No addition on address path: 不会在每次内存访问时加 Base (offset)。无翻译的缺点：任何程序都可以被 link/load 到同个 Physical Address space 区域。

</br>

### B&B with Translation

翻译使保护更容易，⚠️ **程序使用从零开始的虚拟地址，硬件自动加上 Base**：PA = Base + VA —— Valid: **0 ≤ address < Limit** (Limit 是虚拟偏移量)

虚拟地址不等同于硬件地址，由 MMU (HW relocation) 决定最后访问哪一个 physical address。运行时 (**on-the-fly**) 动态通过加偏移量计算物理地址。

</br>

### B&B Insufficiency

- Fragmentation (内存碎片化)：连续分配给进程相同大小的空间容易产生无法利用的空隙 (Internal and External of blocks)
- Missing support for Sparse Address Space：Code、Heap、Stack 之间可能有大量未使用地址，不应该全部占据物理内存。
- IPC (Sharing) 困难：不同进程难以灵活共享部分内存。

于是引出 Segmentation

## Segmentation 分段

分段的思想是：不再把一个进程当成一整块连续内存，而是分成多个独立的 Segment (储存单元细化)，各自有 base&limit (B&B w translation)

例如 Code、Data、Stack 可以分别放在物理内存的不同位置，甚至中间隔着别的进程所属地址。

> Segment 映射由处理器内的 **Segment Registers** 负责。

</br>

### 实现分段

一个 VA 拆成两部分：Segment ID (`Seg #`)、Offset (每个段各自从 0 表示偏移)

处理器维护一个 **Segment Table** (较小，**存在 CPU Processor 而非内存**)，以保存每个分段的 **Base-Limit pair、Validity** (用 1bit 表示是否允许用该段-V/N)。物理内存块数 = `#entries of table`

翻译步骤：

1. 根据 Segment ID (来自VA 的一部分，或者 x86-instruction) 找到对应表项；
2. 检查 Valid Bit；
3. 检查 `Offset < Limit` (防止 out-of-range Error)；
4. **计算 `PA = Base + Offset`**。

</br>

### Example: 16b-VA Segment Translation

16-bit VA 前 2b 表示 Segment ID，剩余 14b 表示 Offset。

![](https://img.nero-lithos.com/posts/%E6%88%AA%E5%B1%8F2026-11-09%2015.47.45.png)

例：VA = `0x4050`：4<sub>HEX</sub> = 0100<sub>BIN</sub>，属于 01 (data) segment；Base = `0x4800`，Limit = `0x1400`；因为 `0x0050 < 0x1400`，访问合法；PA = `0x4800 + 0x0050 = 0x4850`

实际汇编案例中，Instruction Fetch 和 Data Load 都需要地址翻译。例如：

- PC = `0x0364`，取指令的物理地址是 `0x4364`。
- 指令读取的虚拟数据地址是 `0x4050`，对应物理地址 `0x4850`。

这两个地址要分别翻译，不能因为已经翻译了 PC，就直接把数据地址当成物理地址。

</br>

### Pros and cons of Segmentation

- 每次 Load、Store、I-Fetch 都要翻译

- Segmentation 支持不同大小的连续内存块，对 Sparse Address Space 高效，但也因此存在 External Fragmentation (外部碎片：free gaps of spaces between chunks)。这些内存中的空洞，可以允许 Stack/Heap 向 Valid range 之外增长，但也是浪费空间
- Internal Fragmentation：Segment 中不是所有信息都是必要 (存在内存中) 的 —— 需要 **finer granularity** controls

- Segment Table 需要保护：比如 code read-only；data, stack r&w，后文的 Paging 规则一致

- Segment Table 较小，从而存储在 CPU 而非内存；

  **Swapping**：当内存不足时发生 **Context Switch**，为了给下一个进程腾空间，可能把部分或全部 Process Segment Memory 移到 disc，但移动大块数据的开销很高

## Paging 分页

分页是分段产生的 fragmentation 问题的解决方案

> Paging 和 Segmentation 的根本区别：分段使用大小可变的块，分页则把内存划分为固定大小的块。Page 通常比 Segment 小 (1~16KiB)，否则又会有 Internal fragmentation，从而一个段需要占用多页表示。

- Virtual Memory 中的块叫 Page；

- Physical Memory 中的块通常叫 Frame (Page Frame)，每块互相等价 (equivalent)；

- **每个进程维护一个 Page Table** (存储在 Memory) 记录每个 Virtual Page 映射到哪个 Physical Frame，

  以及每页各自的的 Validity, Read, Write 权限；

- 可以用一个 bitvector 表示各个 Physical Page 是 (0) 否 (1) 空闲

固定大小意味着任何空闲 Frame 都能容纳一个 Page，不需要寻找特定大小的连续空间。

> ⚠️ Paging 最重要规律：**Offset 不变** (虚拟-物理页大小必然相等)。Page Table 只负责将 VPN (Virtual Page Number 即 VP\#) 转换成 PFN (Physical Frame Number 即 PP\#) —— \[VPN | Offset] —page table→ \[PFN | Offset]

假设 **Page Size = 2<sup>p</sup> B，意味着 Offset 需要 p bits** 来表示每页中的所有位置，剩余位数为 VPN (2<sup>VPN</sup> bits ≤ Page table 的 entry 数)：

⚠️ **VA = VPN x Page_size + Offset = 2<sup>p </sup>VPN + p**，VPN 就是分页的商 (⌊VA/2<sup>p</sup>⌋)，Offset 是余 (VA mod 2<sup>p</sup>)

- **PA = PFN x Page_size + Offset**

- 当 VPN > Page table size，Access Error (out-of-bound)

如果访问一个无效或权限不允许的 Page，可能产生异常。Page Fault 不一定代表程序崩溃：例如合法的按需分配或换入页面可以由 OS 处理；非法访问则可能导致程序终止。

Stack 向低地址增长时 (需要更多空间)，OS 可以为新的虚拟页分配物理 Frame，并更新 Page Table。**不需要在原 Stack 所在物理地址旁边**找到连续空间。 这正是 Paging 相对于 Segmentation 的重要优势。

</br>

### Example: 4B Pages

Page Size = 4 bytes，所以 Offset 只需要 2 bits；Page Table:

| VPN  | PFN  |
| ---- | ---- |
| 0    | 4    |
| 1    | 3    |
| 2    | 1    |

我们翻译 Virtual Address `0x06`：

1. `0x06 = 6`，所以 VPN = `6 // 4 = 1`；
2. Offset = `6 % 4 = 2`；
3. Page Table 查得 VPN 1 → PFN 3；
4. PA = `3 × 4 + 2 = 14 = 0x0E`。

</br>

### Page Sharing

不同进程拥有各自的 Page Table，但它们的不同 VPN 可以指向同一个 PFN，典型用途包括共享库 (User-level system lib (execute-only))、共享 (Binary) 代码页以及进程间共享内存。

---

| 机制                   | 地址翻译方式               | 优点                 | 主要问题                         |
| ---------------------- | -------------------------- | -------------------- | -------------------------------- |
| Base & Bound（无翻译） | 检查物理地址范围           | 简单                 | 需要 relocation、灵活性差        |
| Base & Bound（有翻译） | Base + VA                  | 隔离进程             | 连续分配、I&E Fragmentation      |
| Segmentation           | Segment Base + Offset      | 逻辑分段、可共享     | 段落连续、E-Fragmentation        |
| Paging                 | PFN x Pagesize + 原 Offset | 非连续分配、易于共享 | Page Table 开销、I-Fragmentation |

---

# CSC3150 Lecture15  Memory: Page Tables & Caching

## Page Table

我们之前讨论的 Single-Level Paging，Page Table 是从 VPN 到 PFN 的映射表 (map)，且每个进程都需要一张 Page Table。因为表结构简单，这张表非常大 —— ～2<sup>VPN</sup> bits (例如 10b offset 的 32 位 VA 需要 2<sup>22 </sup>≈ 4M entries)

核心问题：进程的 VA 很可能是 **Sparse Address Space**，能不能只为实际使用的 VA 区域创建 Page Table？我们将 Page Table 变成一棵树 (Multi-level Page Table)。

---

</br>

</br>

## Two-Level Page Table

双层索引 (“书架-书-页码”)：**P1 每一条有效 Entry 指向一张 P2 Page Table，而 P2 的每个有效 Entry 才指向真正存放数据的 Physical Frame**

对于 32 位 VA，采用 **10-10-12 结构**：

> | P1-index (10bits) | P2-index (10bits) | Offset (12bits) |
> | ----------------- | ----------------- | --------------- |
> | Page Directory    | Page Table        | Byte Offset     |
> | VA >> 22          | VA >> 12 & 0x3FF  | VA & 0xFFF      |

Page_Size = 4 KiB (2<sup>12</sup> B)，所以需要 12b Offset 寻址。如果每个 **PTE** (Page Table Entry) 占 4 B，那么一个 4 KiB 的页表可以存放：2<sup>10</sup> entries。因此每级用 10 bits，就可以表示 2<sup>20</sup> 个页，刚好让每张页表占一个 4 KiB Page，使得总共占用 2<sup>32</sup> B 空间。

1. CPU 中的 Page Table Pointer (例如 x86 的 `CR3`) 指向 P1 页表；
2. 用 P1 找到对应 P2 位置；
3. 用 P2 在二级页表中找到目标 PTE；
4. 取出 PFN，并与原 Offset 组合 (Offset 始终不变)：**PA = PFN x 2<sup>12</sup> + Offset，即 PFN 左移 12 位并加上 Offset，相当于两者拼接**。

**Sparse-Friendly**：单级页表为整个 VPN 空间预留大量表项；多级页表可以让没有使用的地址区域对应的一级 PTE 标记为 Invalid，从而**完全不创建那一块二级页表**。

例如一个进程只在两个相距很远的虚拟区域使用内存：需要 1 个 Page Directory、2 个 P2 Page Table，共占 3 x 4 = 12 KiB，相比 4 MiB 的完整 Page Table 节省很大空间。

但代价是 TLB Miss 时地址翻译可能需要更多次内存访问。

</br>

### PTE

PTE 不只存储 PFN (PPN)，还需要记录访问权限和页面状态。以传统 Intel x86 的 PTE 为例：

- P — Present  页面是否存在于物理内存
- W — Writable 是否允许写入
- U — User 用户态能否访问
- A — Accessed 页面是否被访问过
- D — Dirty 页面是否被修改过
- PCD 是否禁止缓存该页面
- PS — Page Size：PS=1 10b 单层页表 + 22b 索引 (对于 4MB 页)

Invalid PTE 不一定意味着非法地址；可能页面是合法的，但当前不在 RAM 中，例如已被放到磁盘上 (**demand paging**)

**Copy-on-Write** (COW)：UNIX fork() 时子进程获得父进程地址空间的逻辑副本，但如果立刻复制所有物理页面，会非常昂贵——

- COW 允许 fork() 后两个进程**暂时共享物理页** (child 复制 parent 的页表指向同一 PA)，并将两者 PTE 相关映射设为 Read-only，某个进程尝试写入并 **Page Write Fault (Trap)** 后再复制页面，独立 R&W
- 有意利用异常延迟复制，降低 fork() 本身的成本

**Zero Fill On Demand**：新分配的页面不能包含上一个进程留下的敏感数据——

- 将 PTE 标为 Invalid (**Trap**)，OS 等到页面首次使用时再提供一个清零 zeroed 物理页 (就可以在后台 background 创造清零页)

</br>

### Segment-Page Table

**页表树 (多层页表) 的较高层可以采用类似 Segmentation 的结构，使用 Base、Limit 等信息管理下一级页表**

先根据 Segment \# 找到对应的逻辑内存区域，再根据 Page \# 找到该区域内的物理页框

```pseudocode
Virtual Address
┌────────────┬────────────┬────────────┐
│ Segment #  │   Page #   │   Offset   │
└────────────┴────────────┴────────────┘
      │            │             │
Segment Table   Page Table       │
      └──────┬─────┘             │
            PFN                  │
             └─────────┬─────────┘
                Physical Address
```

**Segment Base 指向该 Segment 对应的 Page Table** ⚠️ 而非该 Segment 的数据在物理内存中的起始地址。因为 Segment 内部已经采用 Paging，数据可以分散存储。

Sharing：两个进程拥有各自的 Segment Table，但它们的某个 **Segment Entry 指向同一张 Page Table，甚至无需相同 Segment Number**；但要防备进程间 ⚠️ **Race Condition**。

Context switch **必须保存和恢复当前进程进行地址转换所依赖的顶层状态**，例如：

- 顶层 Segment Registers 的内容；
- 指向顶层 Page Table 的指针。

## 4-Level PT & Inverted PT

即使使用多级页表，最底层对应的物理内存页框，仍然可以通过 [**Bitmap** 位图](https://blog.nero-lithos.com/posts/3150.6/?hl=bitvector) 管理其分配状态：

- **某个虚拟地址映射到哪个物理 Frame**？由 Page Table 解决。

- **物理内存中哪些 Frame 目前是空闲的**？由 Bitmap (由物理内存管理器维护) 解决。

x86-64 的经典 **9-9-9-9-12** 四级页表结构：每张 Page Table 仍然占 4 KiB，但由于 PTE 从 4 bytes 变为 8 bytes，一张表只能容纳 2<sup>9 </sup>= 512 项。**多级页表节省 Memory 空间/sparse-friendly，却可能增加翻译时间/一页要一个指针**。

[**Dual-mode**](https://blog.nero-lithos.com/posts/3150.1/?hl=dual+mode)：进程不能修改自己的页表/段表 (任何 address translation table)，需要 Kernel mode

- 当代 x86 通常有 4 个模式 (**4-rings**)，大多 OS 只用 0-Kernel 和 3-User，称为 **Current Privilege Level** (CPL)。较新处理器支持 1-hypervisor

前面的 **Forward Page Table 都以 Virtual Page 为索引**；而 Inverted Page Table 反向页表改变了思路：主要根据物理页框组织映射记录，并通过 Hash Table 等结构寻找虚拟页对应的物理页，其大小与 VA 无关 (取决于物理内存大小)。对巨大虚拟地址空间 (64 位) 更节省表空间，但有哈希冲突和缓存局部性问题。

## Caching

### I, D, T\$

每次 **Instruction Fetch、Load、Store** [都需要地址翻译](https://blog.nero-lithos.com/posts/3150.6/?hl=I-Fetch)。如果每次都完整遍历页表，CPU-**MMU** 会在查询页表 (多级页表树尤其明显) 上花费大量时间——因此需要[缓存](https://blog.nero-lithos.com/posts/3060.6/?hl=%E7%BC%93%E5%AD%98#cache-definations)。

> CPU 中，处理器向 MMU 发起读写 VA，MMU 利用 Page Table/TLB 翻译为 PA 并查询 CPU-Cache。缓存 hit 时快速返回；缓存 miss 时逐层向下找，直到全部 miss 时离开 CPU，经过 Memory Bus 通过 Memory Controller 找 DRAM。
>
> ⚠️ **所以 MMU 负责每次 reference 时通过 PTE 找 PFN，或当 Invalid 时 Page-Fault 交给 OS 处理**

硬件缓存：通过在MMU 附近存一份较小较快的数据块，在牺牲不频繁任务代价不高的前提下使频繁任务更快。可以缓存 Pages, Files, Address Translations, IP Addresses…

- 除了 Instruction-Cache、Data-Cache 还需要 **Translation Cache** (TLB "Translation Lookaside Buffer")：对于双层页表，如果没有 TLB 且每次查询都需要访问 DRAM，那么一次实际数据访问需要 **3 次 DRAM Access**：一级页表查询、二级页表查询、实际数据访问 (甚至 I/O，如果页表部分在磁盘)
- **TLB Hit** 可以跳过页表查询，直接获得 PFN；**TLB Miss** 则需要进行 Page Table Walk。TLB 与 I-Cache、D-Cache 的作用不同：前者缓存地址映射，后两者缓存实际指令或数据。
- **I-Cache / D-Cache 让获取内容更快，而 TLB 让找到内容所在的物理地址更快**。

</br>

### Principles

[AMAT](https://blog.nero-lithos.com/posts/3060.6/?hl=AMAT) **Average Memory Access Time** (平均内存访问时间) = (HitRate x HitTime) + (MissRate x MissTime) = **HitTime + MissRate x MissPenalty**

- HitRate + MissRate = 1
- MissTime = HitTime + MissPenalty (先尝试命中，失败后访下一层结构)

[**Locality**](https://blog.nero-lithos.com/posts/3060.1/?hl=Locality)：

1. Temporal Locality：访问 A 后的一段时间很可能再次访问 A
2. Spatial Locality：访问 A 后，其邻居，如 A-1、A+1 都很可能被访问

这也是为什么 Cache 通常按 Block 搬运数据，而不是每次只缓存一个 Byte。

1. 这里满足 both localities：

```c
for (int i = 0; i < 99; i++) {
    sum += a[i] + a[i+1];
}
```

2. 二维数组按行遍历 (Row-major) 有很好的 **Spatial Locality**，反之交换内外循环按列遍历就较差。

```c
for (int i = 0; i < 100; i++) {
    for (int j = 0; j < 100; j++) {
        sum += a[i][j];
    }
}
```

### [Cache Block Addressing](https://blog.nero-lithos.com/posts/3060.6/#cache-design)

Cache Block 是缓存的最小存取单位。缓存块地址 (长度和 VA，机器位数相同) 分为 Block Address (商) 和 Block Offset (余)，前者又包含 Tag 和 Index：

> **Address (31~0) = Tag | Index (Set selection) | Byte offset (Data selection)**

- Tag 标识“which block”：区分具体哪个缓存块
- Index 标识“which set”：Set (组) 是一系列缓存块，称为 candidates
- Offset 标识“which byte”：用于选择缓存块中的具体数据，很多缓存实现中没有 data selection field

Cache Block Mapping：**`(block No.) mod (set#)`**

#### 1. Direct-Mapped Cache (1-way Cache)

一个 Memory Block 只能放到一个固定的 Cache 位置：`(block No.) mod (block#)`

对于大小 **2<sup>N</sup> 的缓存区**，最高位 **32～N** 是 Tag；如果缓存块大小 2<sup>M</sup>，最低 M 位 (**0～M-1**) 是 Offset；其余是 Index。

> 类比哈希函数 y = x，适用于大型缓存 (～10<sup>4</sup> entries)

#### 2. Set-Associative Cache

每个 Set 容纳 N 个 Block，称为 **N-way Associative**，一个 Block 放在一个固定的 Set 中任意位置：`(block No.) mod (block# / way#)`

> 类比哈希函数 y = x mod N

#### 3. Fully-Associative Cache

只有一个 Set，容纳所有 Block (或者说 Block 可以放在任意 Cache 位置)

⚠️ 没有 **Index**，如果缓存块大小 2<sup>M</sup>，最低 M 位 (**0～M-1**) 是 Offset；其余是 Tag。

> 类比哈希函数 y = 1，适用于小型/miss 代价极高的缓存 (～100 entries)

---

⚠️ 设 cache size 为 C，block size 为 B (或者 B-bit Addess)，associativity 为 A (A-ways)：

1. 行数 (缓存块数) = C / B
2. 组数 = (C / B) / A ——比如 **direct-mapped 行数和组数相等**
3. 每行实际数据 Cache data bits = B × 8
4. **Index bits = log<sub>2</sub>(\#sets) = log<sub>2</sub>((C / B) / A)** ——比如 **fully-associative** 是 1-set 就**没有 set bits**；**direct-mapped** 的 **set bits 最多**。
5. **Offset bits = log<sub>2</sub>B**，比如 64B block 的 offset 为 6b
6. **Tag bits** = 32 - set bits - offset bits ——从 tag 的额外开销看：**direct-mapped 最省，fully associative 最贵**。

- Block size 越大 或 Associativity 越小，Tag bits 越少；
- Associativity 越高，Set bits 越少 (因为 cache 容量不变时 block \# 固定，set 越大，set 个数就越少)；
- Block size 越大，越好地利用了 spacial locality。

</br>

### Cache Replacement & Miss

如果一个 Set 中的所有 Way 都已占用，新 Block 又要进入，就需要 Replacement：

- Random 随机替换。
- **LRU (Least Recently Used)**：替换最久未使用的 Block。

- Direct-Mapped 不需要选择，因为每个 Set 只有一个位置。

#### [Write-Through vs Write-Back](https://blog.nero-lithos.com/posts/3060.6/#cache-write)

|                  | Write-Through             | Write-Back            |
| ---------------- | ------------------------- | --------------------- |
| 写入时           | 同时更新 Cache 和下层内存 | 先只更新 Cache        |
| 优点             | 一致性管理相对简单        | 减少重复写入下层内存  |
| 缺点             | 写流量较大                | 需要 Dirty Bit 等机制 |
| 替换 Dirty Block | 不需因此回写旧数据        | 必须先回写旧数据      |

#### [Cache Miss](https://blog.nero-lithos.com/posts/3060.6/?hl=coherency#2-decrease-conflict-miss)

| 类型       | 原因                                       | 常见改进             |
| ---------- | ------------------------------------------ | -------------------- |
| Compulsory | 第一次访问某 Block                         | Prefetch             |
| Capacity   | Cache 总容量不够                           | 增大 Cache           |
| Conflict   | 多个 Block 争同一 Set                      | 增加 Associativity   |
| Coherence  | 其他处理器或设备更新数据，导致缓存副本失效 | Cache Coherence 机制 |

# CSC3150 Lecture16  Memory: TLB Caching and Demand Paging

## TLB (continued)

即使系统采用 4-Level Page Table，TLB 仍然缓存最终的 VPN → PFN 结果，而不是只缓存某一级的 PTE。

- 所以在 TLB Hit 时，可以跳过全部级的页表遍历；

- 但 TLB Miss 时也不一定访问 4 次 DRAM，因为中间层的 PTE 本身也可能存在普通 Cache 中。

TLB 的核心 Page Locality：Instruction 高，Stack 存在，Data 较低。

</br>

### Cache 接收的是 VA 还是 PA？

A: Physically-Indexed, Physically-Tagged

- **CPU(VA)→TLB→Cache(PA)**：先翻译，再查 Cache。物理地址决定缓存位置，TLB 可能阻塞索引查找。页表在物理内存中
- 优点：物理地址映射明确；上下文切换时缓存不变 (常见于当代处理器 x86...)

B：Virtually-Indexed Cache

- **CPU(VA)→Cache(VA-index)**：先用 VA index 查 Cache，再翻译。减少等待 TLB 翻译的时间。但存在地址别名、上下文切换问题。页表在虚拟内存中，只有最底层指向物理内存

- 优点：可降低访问延迟 (TLB 不在 critical path)；

因为两个不同的 VA 可以映射到同一个 Physical Page，如果 Cache 直接按 VA 组织，同一份物理数据可能出现在不同缓存位置，造成 **Alias** 问题。所以目前**默认使用 PIPT**。

</br>

### TLB Organization & Protection

普通 Cache 使用 Direct-Mapped 可以减少查找开销。但 TLB 有不同的权衡：

- TLB 通常比较小，如 128–512 entries；
- TLB Miss 的代价较高——可能多级页表遍历；
- 如果 TLB 发生大量 Conflict Miss，性能可能明显下降。

例如一个进程频繁访问 Code、Data、Stack 三个区域，而它们的 VPN 恰好映射到同一个 DM-TLB Entry：

```
Access Code  → TLB Miss
Access Data  → TLB Miss, evict Code
Access Stack → TLB Miss, evict Data
Access Code  → TLB Miss, evict Stack
```

**这种反复互相 evict (驱逐) 叫 Thrashing (反复冲突、抖动)**。因此，⚠️ **小型 TLB 经常采用 Fully-Associative** 设计 (查 VA 返回 PA)，降低冲突风险。当 FA 太慢，放一个 4-16 entries 的超小 DMC ("TLB slice") 在其前面。

TLB Entry (以 MIPS R3000 为例) 包含：

- Translation：VA 查找键、PA 翻译结果
- Protection：Dirty 写入状态、Ref 访问记录、Access 权限 (R/W)、Valid 映射有效性
- Address Space：**ASID Address Space Identifier** 不同进程可能用相同 VPN 但映射到不同 PFN，ASID 使 TLB 区分不同地址空间的映射，减少 Context Switch 时清空整个 TLB 的必要。

⚠️ 优化：**Overlapping (重叠并行)** TLB Lookup & Cache Access

- VA 和 PA 的 **Offset 完全相同**，可以在 TLB 翻译完成前，利用 VA-Offset 访问 Cache。
- 必要条件：**Page Table 和 Cache 对 PA 的划分不一样** ("PFN| PageOffset" vs. "Tag|Index|ByteOffset")，**需要 Cache 的 Index 和 Byte Offset 位全部落在 Page Offset 内**，即 **IndexBits + BlockOffsetBits ≤ PageOffsetBits** 等价于 ⚠️ **CacheSize/Associativity ≤ PageSize**

## Demand Paging

假设程序有 1 GB 的虚拟内存内容，但运行某段代码时只使用 20 MB。如果启动程序时把所有内容读入 RAM：启动慢、占用大、资源利用率低。

90-10 rule：程序 90% 时间都在执行 10% 的代码

Demand Paging 的思想是仅真正访问某 Page 时，才按需将它载入物理内存，类似于“**把 DRAM 当作 Disk 的 Cache**”

> Demand Paging 可以理解成 **Fully-Associative, Write-Back, 1-Page(4K)/Block Cache**
>
> FA：VP-PP 原则上可以任意映射
>
> WB：每次写入内存都同步写磁盘太昂贵，OS 可以先修改 RAM 中的页面，并在需要时回写 Dirty Page。
>
> 有利于将更多程序放到内存中，以促进**更多 concurrency**

</br>

### Page Fault

> **Page Fault 是异常机制，Demand Paging 是利用这一机制实现的内存管理策略**

Page Fault 是 CPU 执行 **Instruction Fetch/Data Fetch** 访问 Virtual Address 时，**地址翻译或权限检查**无法正常完成而产生的 **Synchronous** 异常 (**不是 Interrupt**)。比如 PTE "invalid", Privilege Level Violation, Access violation, does not exist...

课件区分了两类情况：

- Protection Violation：例如写入没有写权限的页面，⚠️ **通常导致 process termination**。
- Recoverable Page Fault：例如合法页面尚未载入 RAM、Stack 缺页，OS 可以修复后重试指令。

**Page Fault 是 Synchronous Exception / Trap**，不是普通的异步硬件中断，因为它由当前正在执行的指令触发。

⚠️ 并非每次 Page Fault 都需要访问磁盘。 Copy-on-Write、Stack Growth、Zero-Fill Page 等情况也可能触发 Page Fault。

</br>

### ⚠️ 总体逻辑

- Program：只需在访问某个 VA 时获得正确的数据，不关心数据实际存储在哪里

Virtual Memory：

- MMU-Page Table：作为 Transparent Level of Indirection (透明映射中间层)：提供 **Flexible Placement** (数据的实际存储位置可以变化，而程序仍然使用相同的 VA)

- Demand Paging：允许页面不始终驻留 RAM，程序可拥有大于实际 RAM 容量的 VA space (**Illusion of Infinite Memory**)

  核心是用 **PTE 的 valid bit** 来标识页是在 RAM 还是 disk

- Page Fault：负责处理缺失页面 (Page Fault 不一定是页面缺失，也可能是权限错误或 Copy-on-Write)

- TLB：缓存最近使用的 Page Table 翻译映射，加速频繁发生的地址转换

</br>

### Page Fault Handling

**Fault**：

1. CPU 访问某个 Virtual Page

   **MMU** 发现 PTE 无法提供 **valid** 映射，触发 **Page Fault Trap**

2. **Traps to OS Page Fault Handler**

   OS 判断该访问是否合法，以及是否可以修复

**OS Replacing Page**：

3. 寻找可用 Physical Frame ("old page")

   优先使用 Free Frame；如果没有，则选择 Victim Page 进行替换

4. 必要时 (**PTE D=1**) **Write Back Dirty Victim**

   如果被替换页已修改，必须在覆盖前保存其内容，并**改其 PTE 及相关 TLB 项为 invalid**

5. 从 **Backing Store** 载入缺失页面

   Disk / SSD 将所需页面读入 Physical Frame

6. **Scheduling on Disk I/O**

   并发：当原进程等待 Disk I/O 时，OS 可以把该进程或线程放到 Waiting Queue，并调度另一个 Ready Process / Thread 执行。

7. 更新 Page Table

   设置新的 PFN、Present Bit 和权限，并处理相关 TLB 状态

8. **重新执行原来的 Faulting Instruction**

   CPU 再次执行导致异常的指令，期望正常执行

使用例：[扩大栈/堆](https://blog.nero-lithos.com/posts/3150.6/?hl=Zero+Fill)、[实现 COW 加速 fork()](https://blog.nero-lithos.com/posts/3150.6/?hl=COW)、**exec()** (RAM 只存 active binary page)、**mmap()** (将文件或共享区域映射到虚拟地址空间-explicit share)

例如 `char *p = mmap(...);` 建立映射后并不意味着整个文件都已经读入 RAM。访问某尚未驻留的页时，OS 通过 Page Fault 将它载入。

</br>

### Backing Store (Swap file)

VA space (VAS) page 在 disk 上的“后备”就是 Backing Store (Swap file)，只有 resident (active) pages 会被映射到 (mapped to) memory frames (PFN)，剩余的需要 OS 记录——

即，当 PTE 无效时，OS 需要记录 `(PID,VPN)→DiskBlock` 映射以找到页面，抽象为 **FindBlock**(PID, \#page) 映射。

- 一般无论是否 resident 的 pages 都可以有 backing store；
- **但页面不一定都在 Swap File 中**：e.g. **Code Segment** 可以直接以磁盘上的可执行文件 (`.exe`) 作为后备存储。若两个进程执行同一程序，只读代码页可以**共享同一 Physical Frame**。**不需要为每个进程都在 Swap 中复制一份相同的代码**。

可以使用 PTE 中尚未被硬件解释的位 / 单独的软件数据结构 / Hash Table (Inverted PT)……实现 (总之在内存)

### Performance Models

#### Working Set Model

WS (工作集) 指某段时间集中访问一个较小的页面集合

如果一个进程当前的 WS 可以完整放入分配给它的 Physical Frames：

- 初始加载时可能有一些 Page Fault；后续访问通常能在 RAM 中命中；Page Fault Rate 会降低。

但如果 Physical Frames 不足以容纳 WS：

- 页面被频繁 Evict，稍后又要重新 Load——大量时间浪费在 **Disk I/O Thrashing**。

增加内存后 Hit Rate 可能突然提高：

- **Hit Rate 随 Cache Size 增加而呈阶梯状上升**，原因是：当 Cache Size 足以容纳一个主要 WS 时，原本频繁发生的 Miss 会显著减少。因此，Cache Hit Rate 并不一定随着 Cache Size 线性提高。

#### Zipf Distribution Model

少数热门数据被频繁访问，而大量冷门数据偶尔被访问，其一般形式：P(r) ∝ r<sup>-α</sup>

这意味着：**Heavy-Tailed Distribution 重尾分布**

- 很小的 Cache 也可能缓存最热门的数据，获得较高 Hit Rate；
- 但由于存在大量冷门数据，即使 Cache 很大，仍然可能发生 Miss。

#### Demand Paging Cost Model

Demand Paging 使用与 [AMAT](https://blog.nero-lithos.com/posts/3150.6/?hl=AMAT) 相同的思想，称为 Effective Access Time (EAT)：

> **EAT = MemoryAccessTime + p x PageFaultPenalty**

（其中 p 是 Page Fault Probability）

计算时会发现 ⚠️ **Page Fault 的代价极高，因此即使 Page Fault Rate 很低，也可能显著降低系统性能**。

**Demand Page** Cache Miss：

1. Compulsory Miss：页面第一次被访问，尚未载入 (fix：prefetching)
2. Capacity Miss：物理内存不足以容纳需要的页面 (fix：增大 DRAM / 调整每个进程占用 RAM 比例)
3. Conflict Miss：**理论上不存在**固定位置冲突 (因为 FA)，因为页面可映射到任意 Frame
4. Policy Miss：页面因为 **Replacement Policy 不合理**而被过早移出 (fix：下一课讨论…)

# CSC3150 Lecture17  Memory: Demand Paging Replacement Policy

假设一个进程需要访问 100 个 Virtual Pages，但物理内存只能容纳 3 个 Page Frames。当进程访问的页面不在内存中，就可能发生 Page Fault。如果物理内存已经满了，操作系统必须选择一个页面移出去，才能加载新页面。

Replacement Policy 的问题就是：Page Fault (Capacity Miss) 时应该替换哪一个页面，才能尽量减少未来的 Page Fault？

- FIFO (Queue)：替换最早进入内存的；简单但可能表现很差

- RANDOM：随机选择；简单但结果不稳定

- MIN (optimal)：未来最晚才会使用的；理论最优，但需要预测未来

- **LRU**：距离现在最久没有使用的；利用过去预测未来 (一种 **approximate-MIN**)

  **Clock：最近未被访问的页面，一种 LRU 的近似实现**

LRU 对于一个特殊序列：`A,B,C,D,A,B,C,D,A,B,C,D` (只有 3 个 Frames，却循环访问 4 个 Pages)

LRU 的运行情况：访问 A、B、C，填满内存；访问 D，淘汰 A；访问 A，淘汰 B；下一次访问 B，淘汰 C……不断重复。结果 **Every reference causes a Page Fault: [THRASHING](https://blog.nero-lithos.com/posts/3150.6/#tlb-organization--protection)!** ——LRU 虽然通常比 FIFO 合理，但并不保证接近 MIN 的性能 (同个序列下，MIN 访问 D 淘汰 C；访问 C 淘汰 B……**only 1/3 reference** cause page fault)。

## Bélády's Anomaly

> **增加物理内存 (frame \#) 理应减少 Page Fault (LRU, MIN 中都如此)；但这个结论对 FIFO 不一定成立**。

比如：A,B,C,D,A,B,E,A,B,C,D,E，在 3-frame 时引发 ABCDABECD (9次) Fage Fault；在4-frame 时反而有 ABCDEABCDE (10 次)。

为什么 LRU 和 MIN 不会出现？因为它们具有 **Stack Propert**y：对于相同的访问序列，使用 k 个 Frames 时保留的页面集合，是使用 k+1 个 Frames 时对应页面集合的子集。

## LRU Implementation

Naive LRU：用一张链表——

- MRU (**Head** Page<sub>2</sub>) → Page<sub>5</sub> → Page<sub>3</sub> → Page<sub>6</sub>  → ... → Page<sub>11</sub> → **LRU** (**Tail** Page<sub>4</sub>)

每次 reference 某一页，就将其移到 Head，这样链表 Tail 永远是 **Least Recently Used Page**。

⚠️ 问题在于：每次内存访问都需要更新数据结构，开销太大。因此实际系统通常使用 **approximate-LRU** 算法。

回忆 [PTE](https://blog.nero-lithos.com/posts/3150.6/#pte) 存储信息中的这两个 bit：

- **A — Accessed/Use bit：页面是否被访问过 (自上次清零后)，1-是**
- D — Dirty/Modified bit：页面是否被修改过 (需要写回 disk)，1-是

</br>

### Clock Algorithm

Clock Algorithm 是一种 LRU-approx.，将物理页面组织成“环形钟点”，并维护一个 Clock Hand (时针)。

Approximation：Replace **an old page**, not **the oldest page** (不保证换走最老页)

实现：每个硬件页 (Frame) 对应在 PTE 有一份 use-bit (A)，每次 Page Fault 时，clock hand 沿环形页面依次扫描，寻找 A = 0 的页面用于替换。

⚠️ **当且仅当发生 Page Fault 时**：

1. 检查 Clock Hand 指向的页面；
2. 如果 `Use = 1`，说明最近使用过，**将它清零，继续移动 (give it a second chance)**；
3. 如果 `Use = 0`，说明有一段时间没用过，选择它作为 Victim Page；
4. **若 Victim D = 1，需要先处理写回**，再加载新页面；否则直接 **evict 并 load new page 到该位置，新页的 A = 1**，然后时针停止转动。

(⚠️ 修改 use bit 时，需要改两处：**TLB** (Cache) 的 A 和 **PTE** 的 A)

特殊的，如果所有页都 used，会绕时钟一圈回到 replace 处 (退化为 **FIFO**)

一般的，时针移动频率越慢越好。0/1 粗略的将页面分为 old/young 两类。

</br>

### Nth-Chance Clock

普通 Clock 给每个 A = 1 页面一次 Second Chance，Nth-Chance Clock 允许页面获得更多机会。

操作系统为每个页面维护一个 **Counter**：

- `Use = 1`：清零 Use Bit，同时重置 Counter；
- `Use = 0`：Counter 增加 1；
- 当 Counter 达到 N：替换该页面，即 clock hand 遇到未使用页 N 次后 replace

N ~ 1K, 是较好的 LRU 近似；N 比较小则更高效 (找到 Replacement 速度快)

Nth-chance Clock 针对 Dirty Pages 的优化：

- Clean Pages：N = 1；Dirty Pages：N = 2

Dirty Page 被替换时可能需要额外写回磁盘，所以**倾向于给予更多机会**。



### No HW A/D bits

如果没有硬件 Accessed / Dirty Bit，操作系统可以故意设置更严格的页面权限，利用 Page Fault 观察访问行为，在 Kernel OS (SW) 中保存这些 bits。

例如 **Software Emulated** Dirty Bit：

1. 初始化所有页为 W = 0，即将本可写的页面也标记为 Read-only；
2. 程序第一次尝试写入，触发 Protection Fault；
3. **OS 检查写入是否合法**；
4. 如果合法，**SW** 记录 `Dirty = 1`，并将页面改为 W = 1。页被写回磁盘时，D = 0，W = 0

> 模拟 Use Bit 则可以将驻留页面暂时标记为 **Invalid**，让首次访问触发异常，再由 OS 记录 Use Bit。

这里的 Fault 是操作系统有意制造的监测机制，不一定意味着页面真的不在物理内存。

## Modern computer systems: memory

核心问题：一台服务器内存不足，而其他服务器有大量空闲内存，能否把其他机器的 RAM 当作 Swap Space？

两种现象：

- Memory-intensive Applications：工作集无法全部驻留内存时，性能可能急剧下降。
- Memory Underutilization：集群中的实际内存使用量可能显著低于分配量。

**Infiniswap** 通过 Memory Disaggregation Layer 利用其他机器的空闲 RAM。

- Application / Virtual Memory Manager：本地机器的内存访问与换页请求
- **Infiniswap Block Device**：作为 Swap Space，路由请求
- Remote RAM：通过 RDMA 访问
- Local Disk：异步备份 (async.) 与容错 (Tolerate remote memory failure)

设计目标与解决方法：

| 设计目标                   | 解决方法                                   |
| -------------------------- | ------------------------------------------ |
| 不修改 application 或 HW   | Remote Paging                              |
| 容忍远程机器故障           | Local Backup Disk                          |
| 支持大规模集群 Scalability | **Decentralized** Remote Memory Management |

其中 RDMA（Remote Direct Memory Access）允许通过网络访问远程内存，并减少远程 CPU 的参与。

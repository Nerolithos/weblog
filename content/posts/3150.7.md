# CSC3150 Lecture18  Modern Memory

## AIFM：应用感知的远程内存

### 背景：Far Memory

一台服务器可能只有 32 GB RAM，但应用需要 100 GB 内存。

传统解决办法包括增加物理内存、使用磁盘 Swap；而 Far Memory 希望利用网络连接的其他服务器上的空闲 RAM。

> Local Server (CPU + 本地 RAM) ↔ Remote Server (空闲 RAM)

通过高速网络访问远程内存：这和上一讲的 Infiniswap 非常接近，但 AIFM 关注的是如何让应用更高效地使用 Far Memory。

</br>

### 传统 Paging 的问题

> **传统 Page 粒度太粗、远程访问开销高**

问题一：**Semantic Gap 语义鸿沟**

OS 知道的是：

- 哪个 Virtual Page 被访问；
- 哪个 Page 需要加载；
- 哪个 Page 应该替换。

但它不知道应用真正想访问什么对象。例如，应用只需要一个 64-byte 对象，OS 却可能需要加载整个 4 KB Page。这叫 **Read/Write Amplification 读写放大**。

而且 OS 不知道应用接下来会遍历链表还是随机查找 Hash Table，因此**很难进行准确的 Prefetching**。

问题二：**High Kernel Overhead 内核开销**

传统远程 Paging 可能需要：触发 Page Fault、进入 Kernel、执行 Page Fault Handler、通过网络获取页面、恢复应用执行。

远程内存访问本来就存在网络延迟，再加上内核处理和 Busy Polling，会进一步降低性能。

</br>

### AIFM Design

| 问题                                  | AIFM 的解决方案                   |
| ------------------------------------- | --------------------------------- |
| Semantic Gap                          | Remoteable Data Structure Library |
| Kernel Overhead                       | Userspace Runtime                 |
| Memory Reclamation 导致暂停           | Pauseless Evacuator               |
| Network Bandwidth 小于 DRAM Bandwidth | Remote Agent                      |

- Remoteable Data Structure Library：让应用使用可远程存储的 Array、List、Hash Table 等数据结构，系统就能利用应用语义。
- Userspace Runtime：尽量在用户态管理远程对象访问，减少传统 Page Fault 路径的开销。
- Pauseless Evacuator：将对象迁移到远程内存时，尽量避免长时间暂停应用。
- Remote Agent：在远程服务器执行部分轻量操作，减少数据往返传输。

普通 `unordered_map`、`array` 可以替换为 `RemHashTable`、`RemArray`，并使用 `DerefScope` 保护访问中的对象不被迁移。AIFM 在实验中显著优于传统远程 Paging 即可

> AIFM uses application semantics and a userspace runtime to reduce the inefficiencies of traditional OS paging for far memory

## PagedAttention：把 OS Paging 思想用到 LLM

### KV Cache

LLM 每生成一个新 Token，都需要利用之前 Token 的 Key 和 Value 向量。如果每次都重新计算过去所有 Token 的 K、V，会浪费大量计算。

因此，模型将已经计算的 K、V 保存起来，这就是 KV Cache。随着生成的 Token 越来越多，KV Cache 也会持续增长。

问题在于：我们无法提前准确知道每个请求最终会生成多少 Token。

</br>

### 传统连续分配

假设某个 LLM 请求预计生成 100 个 Token，于是系统预留了可容纳 100 个 Token 的连续空间。但它最终只生成了 30 个 Token。

剩下的空间可能就被浪费了，三种情况：

| 概念                   | 含义                                   |
| ---------------------- | -------------------------------------- |
| Internal Fragmentation | 分配的空间内部有未使用部分             |
| Reservation            | 为请求未来增长预留的空间，目前尚未使用 |
| External Fragmentation | 不同请求的分配区域之间留下零散空洞     |

这很像之前学习的 Segmentation：不同请求需要大小不等的连续内存块，分配与回收比较困难。

</br>

### PagedAttention

核心思想：不要求一个请求的 KV Cache 在物理内存中连续存储。

例如，一个请求有 10 个 Token，Block Size = 4。

Logical KV Blocks     Block Table（逻辑 → 物理）

Block 0 (0–3)      →       Physical 7

Block 1 (4–7)      →       Physical 2

Block 2 (8–9)      →       Physical 9

逻辑上连续的 KV Blocks 可以映射到不连续的物理位置。

这与 OS Paging 的思想高度相似：

| OS Virtual Memory | PagedAttention       |
| ----------------- | -------------------- |
| Virtual Page      | Logical KV Block     |
| Physical Frame    | Physical KV Block    |
| Page Table        | Block Table          |
| Page Size         | Block Size           |
| 非连续物理分配    | 非连续 KV Cache 分配 |

重点：PagedAttention 不等于操作系统真的在 GPU 上进行传统 Page Fault。 它是借鉴 Paging 的固定大小分块与间接映射思想来管理 KV Cache。

对于 Block Size = B，一个请求的最后一个 Block 最多浪费：B-1 个 Token 的空间

因此，相比按最大输出长度预留连续空间，内存利用率会明显提高。

</br>

### Copy-on-Write

假设 LLM 对同一个 Prompt 生成两个不同答案。两个请求的 Prompt 部分相同，因此可以共享对应的 KV Blocks：Shared Prompt KV Blocks (Reference Count = 2)，独立生成 Output A and B

- 共享时使用 Reference Count 记录引用数。
- 当需要修改共享的物理 Block 时，使用 Copy-on-Write (COW)，分配新的 Block，避免影响其他请求。

这与 `fork()` 后父子进程共享页面、写入时才复制的思路非常接近。

⚠️ 为什么 PagedAttention 可以提高吞吐量？因为它**减少 Fragmentation，并允许共享 KV Blocks，使同样大小的 GPU 内存能够同时容纳更多请求，从而提高 Batching 和 Throughput**

## PF-LLM：LLM 指导硬件 Prefetching

### Prefetching

假设 CPU 正在访问：

```
Address 100
Address 104
Address 108
Address 112
```

硬件发现地址按固定间隔增加，于是预测下次可能访问 116，提前将数据加载到 Cache。这就是 Prefetching 预取。

- Demand Fetch：真正需要数据时才取。
- Prefetch：预测未来需要什么，提前取。目的是减少等待内存数据 (**Cache miss**) 的时间。

</br>

### 传统硬件 Prefetcher

- Slow Convergence：需要观察多次访问才能学会规律。
- Limited On-Chip Logic Budget：芯片面积与硬件资源有限。
- Code Context Unaware：硬件通常难以理解程序代码的语义。

例如，CPU 看到一系列地址，但未必知道它们来自数组遍历、链表遍历还是条件分支。

</br>

### PF-LLM 的思路

不是把一个大语言模型直接放进 CPU 里运行，而是：

- **Offline Analysis**：LLM 分析代码，预测各条 Load Instruction 的访问模式

- Prefetch Hint Table：保存预取策略、预取程度、过滤规则

- **Online Execution**：轻量硬件执行，根据提示选择合适的 Prefetcher

> **PF-LLM moves expensive decision-making offline and leaves lightweight prefetching execution to hardware**

</br>

### Conclusions

- **AIFM** reduces the semantic gap and kernel overhead of traditional far-memory paging.
- **PagedAttention** stores KV Cache in non-contiguous, fixed-size blocks using a block table.
- **PagedAttention** reduces fragmentation and supports block sharing through reference counting and copy-on-write.
- Prefetching predicts future memory accesses to reduce memory stalls.
- **PF-LLM** uses offline LLM-generated hints to guide lightweight online hardware prefetchers.

# CSC3150 Lecture19  File System I: I/O & SDs

SD: Storage Devices

## Device Controllers & Drivers

CPU 并不直接控制外部设备 (即硬盘、键盘等的内部机械/电子结构)，而是通过 **Bus (总线) 另一端的 Device Controller** (设备控制器) 与设备通信。

- CPU 通过读写 **Controller 内部的 Registers** 来发出命令、获取数据、检查设备状态；
- Controller 还可能含有一段存储 **request queue** 的 memory。

处理器通过两种方式访问 DC regs：

- **Port-Mapped I/O**: 独立的 I/O 地址空间 (特殊 `in/out` 指令) 以访问设备寄存器

  E.g. Intel architecture: out 0x21,AL

- **Memory-mapped I/O**: 物理内存地址空间的一部分 (普通 `load/store` 指令) 以访问设备寄存器

  Registers/memory appear in **PA space**

  I/O accomplished with standard load & store instructions

⚠️ Memory-Mapped I/O **并不意味着设备寄存器真的存储在 RAM 中**，只是将特定物理地址映射到了设备。

</br>

### Programmed I/O vs. DMA

**Programmed I/O (PIO)**：CPU 发出请求，接收设备数据，再由 CPU 将数据写入内存。缺点是占用大量 CPU 时间。**Device → CPU → RAM** (CPU 负责搬运数据)

**Direct Memory Access (DMA)**：CPU 初始化 DMA 请求，设备控制器直接通过总线向 RAM 传输数据，完成后再 **Interrupt** CPU。**CPU ↔ Device → RAM** (设备直接与 RAM 传输数据)

DMA 的重点不是让设备本身读写得更快，而是减少 CPU 参与数据搬运的开销，让 CPU 可以同时执行其他任务。

- DMA completely eliminates CPU involvement. — False
- DMA allows data transfer without continuous CPU involvement. — True
- DMA can use interrupts to notify the CPU of completion. — True

</br>

### Device Driver

**Device Controller 是硬件，而 Device Driver 是负责与设备硬件交互的软件**，在本课件中主要指 Kernel 中的驱动代码。它的作用是隐藏不同设备的硬件差异 (**Illusionist**)，让 OS 使用**统一接口**，例如 `read()`、`write()`。Driver 分成两个部分：

1. **Top Half**：**System Call 调用路径**触发，用于发起 **I/O 请求**，可能使线程 Sleep；
2. **Bottom Half**：[Hardware **Interrupt**](https://blog.nero-lithos.com/posts/3150.1/#memory-protectionbb-and-addressing) 触发，用于处理 I/O 结果，可能 Wake Up 线程。

一个典型的 Blocking I/O 生命周期：

1. 用户程序调用 `read()`，Kernel 检查是否已有可用数据
2. 若没有，**Driver Top Half 向设备发出请求**，调用线程进入 **Sleep**
3. 设备执行 I/O，CPU 可以调度其他线程
4. 设备完成 I/O，产生 **Interrupt**
5. **Driver Bottom Half 处理结果**，唤醒等待线程
6. 线程重新获得 CPU，System Call 返回

## SD I. HDD (基于 Magnetic Disc)

> **File systems**：最常见的 storage devices 之上的 abstraction，让用户将数据整理进 [**named files / hierarchical paths**](https://blog.nero-lithos.com/posts/3150.2/?hl=sequence)。

衡量 **SDs Performance**：

- **Latency**: 任务完成的 **time**

- **Throughput / Bandwidth**: 任务进行的 **rate** (bytes/ms, ops/s, etc.)

- **Start up / Overhead**: operation 开始的 **time**

  Most I/O operations are roughly linear in b bytes，Latency(b) = Overhead + b/TransferCapac

</br>

### Blocking、Non-blocking、Asynchronous I/O

> 回忆 Scheduling 部分：“线程等待 I/O 时处于 **Blocked** 状态，而不是 [Busy Waiting](https://blog.nero-lithos.com/posts/3150.3/?hl=Busy)。”

三种 I/O 类型：

- **Blocking** Interface：r/w 调用后等待 (调用线程 Sleep) 直到 Device ready

- **Non-blocking** Interface：“我以后再试”，调用后不等待 (立即返回当前结果或未就绪状态，当前能完成多少就返回多少)

  **从读写请求中迅速返回，并返回已经成功传输的字节数**；读写可能都空返回；如果无数据可读则返回 `-1` error ("operation would **BLOCK**")

  ⚠️ 未完成情况下，后续 I/O 需要**用户程序**再次调用 `read/write`

- **Asynchronous** Interface："稍后告诉我"，调用后不等待 (立即返回，并请求继续执行，完成后通知用户)

  ⚠️ 不同于 Non-Blocking，后续 I/O 由 **Kernel 后台执行**，完成后 **Notification 被动通知 / Poll 主动轮询**

  ① **Read**：用户提供指向 User **Buffer** 的指针，Kernel 在后台读取完后填入缓冲区，完成后 Notify/Poll；

  ② **Write**：提供 Buffer 指针，Kernel 在后台从 Buffer 获取数据并执行写入，完成后 Notify/Poll

</br>

### ⚠️ SD Media 存储介质

- **Magnetic disks** 磁盘：通过磁化状态**低成本大容量**地存储数据

  **HDD** 的载体部分，可原地覆盖，需机械运动 (易损)，无并行

  Block-wise **random access** 较慢 (10ms)，**sequential access** 稍快，读有局部性

  数据很少发生损坏 corruption

- **Flash Memory** 闪存：通过电子存储电荷状态**高成本小容量** (5-20x disk) 地存储数据

  **SSD 和 U盘**的载体部分，需 Block-wise 擦除后修改，无运动部件，Bank-并行

  Block-wise **random access** 较快(10μs)，**random write** 更差，读没有局部性

  数据很少发生损坏 corruption

  **Wear patterns 磨损问题**：由于需要擦除修改，某些常用块可能出现**不均匀磨损**

</br>

### HDD (Hard Disk Drive)

- **Platter 盘片**：存储数据的盘片 (同个设备包含多个盘)，有两面 (surface)

- **Track 磁道**：盘片表面的一条同心圆磁道 (concentric circle)

  通常只有外半圈的磁道被使用

- **Sector 扇区**：一条磁道上的一个扇区，最小可寻址的物理传输单位

  HDD **外圈磁道拥有更多 Sector per Track**，因此外圈通常有更高 **Bandwidth** (顺序传输)

- **Cylinder**：所有盘面上相同半径的磁道的集合

  访问同一个 Cylinder 内的不同磁道，不需要移动整个磁头臂进行径向寻道

- **Head 磁头**：位于**磁臂 (Arm)** 尖端用于读写数据的磁头，

  **磁臂马达选中目标磁道，盘片马达选中目标扇区**

![](https://img.nero-lithos.com/posts/%E6%88%AA%E5%B1%8F2026-11-26%2011.20.38.png)

#### HDD R/W Latency

读取 HDD 上的数据需要三个主要耗时步骤，磁盘优化通常面向前两项——

- Seek Time：**旋转磁头到目标的 Track** 所需时间

- Rotational Latency：**旋转盘片到目标 Sector** 位于磁头下方所需时间

  **T<sub>rot.</sub> = 60/RPM (s) or 60000/RPM (ms)**

- Transfer Time：实际读取或写入数据

  **T<sub>trans.</sub> = Block Size (B) / Transfer Rate (B/s)**，(⚠️ [MB = 10<sup>6</sup> B, MiB = 1024<sup>2</sup> B](https://blog.nero-lithos.com/posts/3150.6/?hl=KiB))

> **Request Time = Queueing Time + Controller Time + Seek + Rotational + Transfer**

HDD 的**随机访问性能可能比顺序访问差 100 倍以上**。不是因为 HDD 读取数据的速度变慢了，而是因为每次随机访问都要承担巨大的机械定位开销 (**Seek 和 Rotation 远慢于 Transfer**)。

</br>

### Disk Scheduling

和之前学过的 CPU Scheduling 类似，Disk 同时只能响应一个 request，当有多个 I/O Request 等待处理时 OS 决定先处理哪一个。不过 CPU Scheduling 主要考虑执行时间、公平性等因素；HDD Scheduling 还必须考虑**磁头移动距离**。

1. **FIFO (FCFS)**：按请求到达顺序执行，缺点是磁头可能频繁往返
2. **SSTF (Shortest Seek Time First)**：类似贪心算法，优先处理离磁头最近的请求，缺点是可能造成 **Starvation** ——磁头附近不断出现新请求，远处的请求可能一直不处理
3. **SCAN (Elevator Algorithm)**：沿一个方向优先处理该方向上距离最近的 I/O 请求，到达边界后反向，缺点是中间区域通常更有优势。它既**减少 Seek Time**，又避免 SSTF 的饥饿问题
4. **C-SCAN (Circular Scan)**：只在一个方向处理请求，环形访问 (跨越边界)，比 SCAN 更公平，缺点是返回起点时不处理请求

![](https://img.nero-lithos.com/posts/wiyfgwieuf.png)

**Shingled Magnetic Recording (SMR)**: pack more data with **error correcting codes**

- 写磁头比读磁头区域更宽，overlap 多个 track

- 隐藏写导致 track 上周边发生 corruptions (但必须在后台修复)

**Sector sparing**: 将问题扇区隐式 remap 到同一盘片面上的其他空扇区

**Slip sparing**: 为维持 sequential 高效性，在某扇区出问题时 remap 所有扇区

**Track skewing**: 扇区编号 offset 跨 track 连续，从而允许 sequential ops 时磁头移动

## SD II. SSD (基于Flash Mem.)

### SSD (Solid State Drive)

SSD 基于**没有运动部件** (没有马达) 的[闪存](https://blog.nero-lithos.com/posts/3060.6/?hl=%E9%97%AA%E5%AD%98)，也就**没有磁盘的 seek / rotational delay**，较轻且较低功耗，缺点是**修改不能直接覆盖而要先擦除，擦除会导致硬件老化**。闪存结构：

- Bank：不同 Bank 可以并行 **parallelism** 访问，包含多个 Block

- (Flash) Block：通常 128/256 KB，含多个 Page，是**擦除单位**，通常含 64～258 个 Page

  Flash Block 和 Cache/Memory Block 不是同个东西

- Page：通常约 4 KB，是读写单位，包含多个 Cell

- Cell：存储 1–4 bits，其中用电子表示 0/1

  SLC (Single-level Cell): **1-bit-per-transistor**，更快更长寿 (50~100k Writes)

  MLC (Multi-level Cell): transistor 通过不同**电荷水平 (charge level)** 表示 2~3 bit，**老化更快** (1~10k Writes)

</br>

### Low-level flash operations

> ⚠️ **Write = Erase + Program，只有 "`Erased`" page 可以 Program**，为提供和 HDD 相同的接口 (interface)，SSD 提供 3 个主要的 Low-level flash operations：

1. **Read(page_No)**：按 Page 读取，与前一次读位置无关 (无局部性)，Latency 为数十 **μs**
2. **Program(page_No)** 即 Write：按 Page 将部分 bit 从 1 写成 0 并记为 `Valid` (⚠️ 不可连续重复 program 同一页，必须先擦除所属 Block)，Latency 为数百 **μs**
3. **Erase()**：将整个 Block 所有 bits 恢复为 1 并全部记为 `Erased`，Latency 为 **ms 级**

**Write Amplification** = Physical_Write_Traffic / OS_Issued_Traffic：问题是只修改 Page 0也会导致同 Block 中 Page 1、2、3… 的数据全部擦除。如果要保留其他数据，就必须先读取它们，再擦除整个 Block，最后重新写入。这既慢，又会消耗 Flash 的有限擦写寿命。

</br>

### Flash Translation Layer (FTL)

用于**减少写入的 Wear and Write Amplify**，FTL 引入了两个系统设计思想老朋友：**[Indirection 间接映射](https://blog.nero-lithos.com/posts/3150.6/?hl=Indirection#-%E6%80%BB%E4%BD%93%E9%80%BB%E8%BE%91)—VA不变PA变 + [Copy-on-Write 写时复制](https://blog.nero-lithos.com/posts/3150.6/?hl=COW)—写部分拖慢整体操作时的经典对策**

- Indirection：OS 使用的是 Virtual Block Number，SSD 内部使用的是 Physical Page Number。FTL 作为 Layer of Indirection **在 DRAM 维护一个 Mapping Table** 用于翻译 (将两者关联)。
- COW (Log-structured FTL)：当 OS 要更新一个 Page 时，**不再覆盖原来的 Physical Page，而是写入一个空闲新 Page**，然后更新 Mapping Table 改指向它。

**Garbage Collection (GC)**：回收包含失效 Page 的 Block。如果一个 Block 中既有 Valid Page，又有 Invalid Page，GC 必须先把仍然有效的数据迁移到其他位置，再擦除整个 Block。因此，GC 本身也可能造成 Write Amplification。

**Wear Leveling (磨损均衡)**：尽量让不同 Flash Block 的擦除次数均匀分布，避免某个 Block 因频繁写入而过早损坏。

## File System

[Illusionist](https://blog.nero-lithos.com/posts/3150.1/?hl=Illusionist)：硬盘 (SD) 本身只提供一种非常简单的抽象：一个可以读写的 Block Array。它并不知道什么是 PDF、图片、文件名或者文件夹。File System 是一层负责将底层 Block Array Interface 转换成用户熟悉的文件和目录结构抽象的 **OS**。

![](https://img.nero-lithos.com/posts/doiyufgouif.png)

File 在不同计算机不同部分看来完全不同——

- User：Durable **Data Structures** 可靠的数据结构

- System (Syscall interface)：[Collection of Bytes](https://blog.nero-lithos.com/posts/3150.2/?hl=Sequence) (UNIX)

- System (OS)：Collection of **blocks** (块-虚拟寻址单元)

- SD (E.g. HDD Hardware)：Collection of **Sectors** (扇区-物理寻址单元)

  **Block size ≥ sector size，UNIX block size = 4KB**

  **LBA (Logical Block Addressing)**：每个扇区拥有整数地址，Controller 将地址翻译为磁盘上的物理位置 (OS 无需了解磁盘物理结构)。File System 需要在磁盘某处记录空 Block、Block-File 映射、Directory 并在使用时实时分配 File 大小

**Read-Modify-Write**：如果用户想修改文件中第 2–12 个 Byte，文件系统可能需要读 4096 Byte (整个 Block)、修改其中对应的 Bytes，再 WB 整个 Block。若该 Block 已在内存 Cache 中，就不需要从磁盘读取。

</br>

### Components of File System

- Superblock object: 保存整个 File System 的基本信息

- Free bitmaps: 记录哪些空间已 allocated，哪些仍然空闲

- [Inode](https://blog.nero-lithos.com/posts/3150.2/?hl=inode) (Index Node) object: 表示一个具体的文件

  **Index Node 是描述一个文件的[元数据 metadata](https://blog.nero-lithos.com/posts/3150.2/?hl=metadata) 结构**， UNIX Inode 包含文件大小、权限、所有者、时间戳，以及定位文件数据块所需的信息。⚠️ **文件名通常不存储在 Inode 中，而是存储在 Directory Entry 中**

- **Dentry (Directory Entry)** object: 文件名与文件之间的目录映射，single component of a path

  **每个 <file_name : inode> 映射就是一项 Dentry**

- [File object](https://blog.nero-lithos.com/posts/3150.2/?hl=instance): 表示进程打开的文件 (回忆 fd!)
- Blocks: (磁盘上) 存储实际文件内容

整个文件查找过程可以理解为 File Name (Dentry) → Inode → Data Block

Directory 本身也是一种特殊的 File，其内容是 `<file_name : inode_number>` 映射。这也解释了为什么同一个文件可以有多个名字 (Hard Link)：**多个 Dentry 可以指向同一个 Inode。**

</br>

### File Descriptor 与 Inode 的关系

![](https://img.nero-lithos.com/posts/%E6%88%AA%E5%B1%8F2026-11-27%2019.01.22.png)

> **fd** 保存指向 Open File Description 的引用，每个 Process 独有
>
> [**OFD**](https://blog.nero-lithos.com/posts/3150.2/?hl=OFD#file-descriptor--open-file-description) 保存 Exec_Mode、File_Offset、Flags、**Inode Number**，以 OFD Table 形式存在 Kernel 中
>
> **Inode** 保存文件元数据和数据块定位信息，作用于 File System

```c
int fd1 = open("foo.txt", O_RDONLY);
int fd2 = dup(fd1);
int fd3 = open("foo.txt", O_RDONLY);
```

- `fd1` 和 `fd2` 共享 OFD，因此共享 Offset；
- `fd3` 拥有独立的 OFD，因此 Offset 独立；
- 三者都指向同一个文件的 Inode。

```c
int fd = open("/foo/bar.txt", O_RDONLY);
read(fd, buf, 4096);
```

1. 读取 Root Directory 的 Inode。
2. 读取 Root Directory 的 Data Block，找到 `foo` 对应的 Inode Number。
3. 读取 `foo` 的 Inode。
4. 读取 `foo` Directory 的 Data Block，找到 `bar.txt` 的 Inode Number。
5. 读取 `bar.txt` 的 Inode，获得文件元数据及数据块定位信息。
6. `open()` 建立 OFD，返回 fd。
7. `read()` 根据 Offset 和 Inode 定位并读取对应的 Data Block。

因此， 在没有缓存的简化模型中，`open("/foo/bar.txt")` 本身就可能**需要多次 Disk I/O**，即使还没有调用 `read()`。每次 `read()` 后可能发生 **Inode Write**，这通常是为了更新文件的 Access Time 等元数据，而不是修改文件内容。实际系统通过缓存和不同的时间戳更新策略，可以避免每次读取都产生这些磁盘操作。

## 调音台

想象一台**拥有数十亿乃至数万亿个旋钮的智能调音台**。输入音频，有些旋钮控制高低频，有些控制不同输入间的混合比例……所有旋钮互相配合，最终影响输出的音乐。对于人声和电子乐，它可以产生不同处理效果。

![](https://img.nero-lithos.com/posts/Recording%20studio%20mixing%20desk%20close-up.jpg)

**大模型的参数 (i.e. 权重, Parameters)，就相当于这些旋钮的位置**。

满血 **DeepSeek-V3 拥有 671B 参数**，其中 **B 代表 Billion (十亿)**。按照我们的类比，相当于一台拥有 6710 亿个可调旋钮的超级调音台。所谓“蒸馏”就意味着模仿原调音台的效果训练一台旋钮数量更少的调音台。

不过，这些旋钮**并非每个都独立对应一种明确功能**，而是通过复杂矩阵运算共同影响最终输出。模型在训练过程中不断调整这些旋钮，**训练完成后，旋钮位置通常就固定了**，使用时改变的只是输入“音频”，只有进行微调 (如 LoRA) 等操作才会改变参数，所以一般认为商业类 LLM 无法“学习”；这恰好与调音板类似，音效师调好后除了控制音量的推子，你也不会想乱碰旋钮的。

但处理每个 Token 时 6710 亿 个参数都参与计算量太大 (尤其对于 PC 本地部署)，DeepSeek-V3 采用著名的 **MoE (混合专家) 架构**：虽然依然总共存储 671B 参数，但处理每个 Token 时仅激活约 5%，即 **37B 参数**。仍然像调音台那样——处理人声时，去齿音器、滤波器之类的旋钮工作；输入背景配乐时，则是音量限制器、避让人声等旋钮生效；输入 AI Slop 司凤音乐时直接消音……总之，你懂我意思，每次处理输入时只需要启用其中一部分处理模块，而不必让全部模块同时 Active。

你或许注意到 MoE 不会减少某一模型的内存/显存占用，这属于“**量化**”的活——或许你没亲手摸过调音台，**想象鼠标滚轮或挂顶式电风扇旋钮**，转起来越顺滑说明档位越多、精度越高，比如一个四档电风扇就有“2-bit 精度”。而  为 **FP8** 精度 (每个参数作为半精度浮点数占 1 Byte)，整体权重就占 671 GB。若将它压到 2-bit，精度和显存大小减少 75%。

很好，量化后的模型终于能挤进显存，那它就能本地运行吗？对……又不对。在 16GB 显存的显卡 (GPU VRAM) 运行一个 13GB 的量化模型。**权重不是唯一需要显存的东西**，还有 LLM 永远的坎：上下文。之后会讲到的 LLM 的计算模块 (**Transformer**) 处理每个 Token 时，还会用 **KV Cache** 保存它在神经网络各层计算中产生的 Key 和 Value，供后续 Token 直接复用避免重复计算。优化 KV Cache 主要靠 MLA。

但这些缓存可以在不同请求间复用，形成我们常说的 **Prompt Cache**：在不同请求间复用已有的前缀 Token 计算结果，底层通常也利用 KV Cache，这就是我们常说的大模型“**缓存命中率**”所谓之缓存。

总之，上下文越长，KV Cache 占用的显存通常正比例的增大。DS-V3 每个 Token 约占用 70KB 的缓存，**短短 32K 上下文就需要 2.3GB**，写代码的话，对话轮数两只手就能数清。而读取这些缓存和计算都受**显存带宽**制约，只能说慢跑也是跑。

如果显存实在不够，还可以通过 **CPU Offloading** 将部分模型层放进系统内存，但这样又会受到 CPU 算力、系统内存带宽，以及 CPU 与 GPU 之间的 **PCIe 总线带宽**限制。

## Tokenization、Embedding、Transformer、Diffusion

调音台接收的是电信号，而不是“分子振动发出的波”，或者说声音。类似的，大模型也不能直接对自然语言进行矩阵运算。

```
宇宙的终极答案是四十二
→ ["宇宙", "的", "终", "极", "答案", "是", "四十", "二"]
→ {[0.1345, 1.24623, ...], [0.01193, 0.114514, ...], ...}
```

模型会先把它切成若干 Token，然后让每个 Token 对应一个高维数字向量 (embedding)。Token 不一定是一个完整字词 (甚至不同模型间也不同)，而是模型按照统计规律切分出来的文本片段；它不一定有独立语义，却是模型理解和生成语言的基本单位。

Embedding 本身通常也是训练出来的模型参数的一部分，如果它们是在一个具有语义结构的空间中学习得到的，那么相近概念的向量方向通常也更接近：苹果更靠近香蕉而不是 M200 狙击步枪。

假设你突然想听电子乐，调音师可以学习曲风并重新调整旋钮，或者干脆直接找一首电子乐输入。后者就是 RAG (Retrieval-Augmented Generation) 检索增强生成的核心思想：问题 + 检索资料 → 模型回答，而全程模型参数不需要改变。

Embedding 在 RAG 中也经常出现。例如先把 10,000 份文档转换成向量，用户提问时也生成一个查询向量，然后检索语义上最接近的文档片段，再交给大模型。这就像**用一套自动检索系统，不管要听啥曲风，把合适的乐谱找到并摆到已经调试好的调音台前面**。
